TypeScript · Fastify · PostgreSQL · argon2id.

## التشغيل

```bash
pg_ctlcluster 16 main start     # تشغيل PostgreSQL
npm install
./db.sh                         # إنشاء قاعدة darsy ودورها وتطبيق الهجرات
npm run dev                     # الخادم على المنفذ 3000

npm run test:all                # قيود القاعدة + التحقق من الأنواع + اختبارات المصادقة
```

## المصادقة

| المسار | ما يفعله |
|---|---|
| `POST /api/auth/signup` | حساب جديد (طالب · ولي أمر · مدرس فقط) + رمز تحقق |
| `POST /api/auth/login` | دخول بالدور والرقم وكلمة المرور |
| `POST /api/auth/refresh` | تدوير الجلسة |
| `POST /api/auth/logout` | إبطال الجلسة الحالية |
| `POST /api/auth/verify-phone` | توثيق الرقم بالرمز |
| `POST /api/auth/resend-code` | رمز جديد (بمهلة 60 ثانية) |
| `POST /api/auth/forgot` · `/reset` | استعادة كلمة المرور |
| `POST /api/auth/change-password` | تغييرها من داخل الحساب |
| `GET /api/auth/me` | بيانات صاحب الجلسة |

### قرارات أمنية مقصودة

- **كلمات المرور بـargon2id** (الصيغة المقاومة للذاكرة)، ولا عمود نصي لها في المخطط أصلًا.
- **رموز التحديث تُخزَّن مجزّأة** مثل كلمات المرور — قاعدة بيانات مسروقة لا تمنح جلسة عاملة.
- **تدوير مع كشف السرقة:** استعمال رمز تحديث مرتين يعني أنه نُسخ، فتُقطع **كل** جلسات المستخدم.
- **رسالة واحدة** لرقم غير مسجل ولكلمة مرور خاطئة — التمييز بينهما يكشف أي الأرقام لها حسابات.
- **`/auth/forgot` يردّ الرد نفسه دائمًا** للسبب ذاته.
- **قفل بعد 5 محاولات** لكل رقم، مستقل عن الـIP: الهدف الحساب لا الاتصال.
- **رموز OTP مجزّأة**، صلاحية 5 دقائق، 3 محاولات، وطلب رمز جديد يُبطل القديم.
- **تغيير كلمة المرور يُنهي كل الجلسات.**
- **الكعكة HttpOnly · SameSite=Strict · Secure في الإنتاج** — ولا رمز في `localStorage`.
- **الإنتاج يرفض الإقلاع بمفتاح التطوير.**

`db.sh` **يحذف القاعدة ويعيد بناءها** — للتطوير وحده. الإنتاج يستعمل هجرات تراكمية
عبر `node-pg-migrate` كما في مستند البنية التقنية.

## لماذا SQL يدوي لا ORM

قيمة هذا المخطط في **القيود والمشغّلات والفهارس الجزئية**، وهي ما تُسقطه معظم أدوات
الـORM حين تولّد المخطط بنفسها. الهجرات تُكتب هنا يدويًا، وأي ORM يُستعمل لاحقًا
يكون **للاستعلام فقط**.

## ما تفرضه قاعدة البيانات — وما يبقى على التطبيق

| القاعدة | كيف تُفرَض |
|---|---|
| العمولة + نصيب المدرس = السعر | `check` على الحجز وعلى الحركة |
| لا حجزان فرديان مؤكدان لنفس المدرس والموعد | فهرس فريد جزئي |
| لا رصيد سالب | مشغّل فوري بقفل صف |
| لا حركتان ماليتان لحجز واحد | `unique(booking_id)` |
| لا تعديل لقيمة حركة مسجّلة | مشغّل يمنع تغيير `gross_amount` |
| لا Webhook يُعالَج مرتين | `unique(provider, event_id)` |
| تقييم واحد لحجز **مكتمل** | `unique` + مشغّل يقرأ حالة الحجز |
| الحجز لمتعلّم تحت حسابك وحده | مشغّل يقرأ `children` |
| إيقاف فعّال واحد لكل مدرس | فهرس فريد جزئي |
| صيغة رقم الهاتف · حدود السعر · مقاعد الجماعية | `check` |
| اختيار شريحة العمولة · آلة حالات الحجز · صلاحية الدور | **التطبيق** |

## دروس من كتابة الاختبارات

**١. `or` في قيد `check` فخّ.** الصيغة البديهية

```sql
check ((kind = 'group' and group_seats between 2 and 12)
    or (kind = 'individual' and group_seats is null))
```

تمرّ على جلسة جماعية بلا مقاعد: `NULL or FALSE` يساوي `NULL`، و`check` يعتبر `NULL`
نجاحًا. الصيغة الصحيحة بـ`case` تُعيد `true/false` دائمًا. كشف هذا الاختبار وحده.

**٢. القيد المؤجَّل لا يصلح هنا.** `deferrable initially deferred` يفحص الرصيد عند
الـcommit — بعد أن يكون الـAPI قد ردّ على المستخدم. جُعل فوريًا ليصل الرفض في حينه.

**٣. لا اتصال بصلاحيات مدير القاعدة.** `db.sh` ينشئ دور `darsy` منفصلًا ويمنحه القاعدة
وحدها؛ التطبيق لا يتصل بحساب `postgres` في أي بيئة.
